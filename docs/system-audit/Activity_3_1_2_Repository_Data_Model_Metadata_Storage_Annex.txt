1. Purpose, Scope and Design Principles
This Annex defines the repository's logical data model, enforceable metadata dictionary, controlled 
vocabularies, storage zones, identifiers, versioning, AI lineage, ethical governance and acceptance tests.
 DM-01  Store canonical objects once and apply access policy through metadata and authorization 
rules rather than security-labelled canonical folders.
 DM-02  Separate participant identity information from research and repository metadata.
 DM-03  Treat consent, collective cultural protocols, embargoes and curator decisions as distinct, 
versioned governance evidence.
 DM-04  Preserve immutable provenance from source capture through derivatives, datasets, models, 
embeddings and releases.
 DM-05  Operate the primary repository, backups, search and AI services entirely on JOOUST-
controlled on-premises infrastructure.
1.1 Interpretation rules
 The most restrictive applicable active rule determines effective access.
 Withdrawal affects source records, derivatives, releases, datasets, embeddings and deployment 
registers.
 Exact GPS and identity data are protected attributes and are not general discovery metadata.
 Controlled-vocabulary values are stored as codes with human-readable labels; free text is used only 
where explicitly permitted.
 Published and research dataset releases are immutable. Corrections create a superseding release 
and retain a tombstone for the withdrawn object.

4. Relationship and Integrity Rules
Rule ID Constraint Required implementation
REL-01 MediaAsset and ConsentRecord are many-to-many. AssetConsent junction with asset_id, consent_id, coverage role, valid_from and valid_to.
REL-02 Sessions and Domains are many-to-many. SessionDomain junction; one row may be flagged primary.
REL-03 Cultural records may have individual and collective contributors. RecordAgent junction using Agent; no polymorphic nullable foreign keys.
REL-04 Restrictions apply to multiple object types. GovernedObject registry plus restriction-target junction, or type-specific junctions with database constraints.
REL-05 Transcripts and translations are versioned. Unique(asset_id, language_code, version_no); prior versions remain immutable.
REL-06 Repository items and releases are many-to-many. ReleaseItem with approval evidence and object checksum.
REL-07 Deletion must not orphan audit/provenance. Restrict deletion of referenced rows; use lifecycle state and tombstones.
REL-08 Checksums identify exact byte streams, not intellectual duplicates. Unique storage_object_key; index SHA-256 and record duplicate review status.

4.1 Key database constraints
 Use UUID primary keys internally; retain human-readable session_id and asset_id as unique 
alternate keys.
 Use foreign keys with ON DELETE RESTRICT for consent, provenance, releases and audit 
relationships.
 Use CHECK constraints for enumerated lifecycle states and ISO language/date formats.
 Use partial unique indexes for one active canonical derivative or approved version per role where 
required.
 Index project, session, county/site, domain, restriction, consent status, checksum, workflow status 
and capture date.
 Use PostGIS geometry for precise locations in a protected schema; expose generalized site geometry 
to ordinary searches.

7. Consent, Cultural Protocol and Effective Access
7.1 Effective-access calculation
The authorization service shall evaluate all active rules for the requested object and its source lineage. The 
result shall be the most restrictive applicable level.
Priority Rule source Decision effect
1 Withdrawal or legal/ethical hold Deny use; start propagation workflow.
2 Sacred/restricted community protocol Limit to expressly authorized custodians or deny.
3 Active embargo Deny until embargo expiry unless an approved exception exists.
4 Participant consent scope Limit to permitted research, teaching, excerpt or community use.
5 Curator publication decision May further restrict; may never broaden beyond consent/protocol.
6 Role and project authorization Allow only where user role and purpose match effective access.
7.2 Withdrawal propagation
 Open a WithdrawalCase and freeze affected publication/export actions.
 Resolve all source assets and dependent transcripts, derivatives, repository items, datasets, releases, 
embeddings and model registers through provenance links.
 Remove or suppress affected objects from active access and create tombstone records where 
auditability requires retention.
 Rebuild affected release manifests and embedding indexes; issue a superseding release rather than 
altering an immutable release silently.
 Assess trained models. Record whether retraining, output filtering, deployment withdrawal or 
documented residual-risk acceptance is required.
 Close the case only after technical and governance reviewers sign the evidence record.

8.1 Training eligibility
 AI-DM-01  Record training_eligible, eligibility_basis, evaluated_at and evaluated_by for each dataset 
member.
 AI-DM-02  Do not treat public visibility as automatic permission for model training.
 AI-DM-03  Split train/validation/test data by verified session, site or source group to prevent leakage.
 AI-DM-04  Retain excluded-object reasons and duplicate/quality review outcomes.
 AI-DM-05  Link every deployed model and embedding index to the exact governed dataset/source 
snapshot.

10. Retention, Deletion, Backup and Recovery
Control Requirement
Retention schedule Assign every governed object a retention_class, review date and accountable owner.
Secure deletion Use approved on-premises deletion procedures; verify canonical, derivative, cache and backup treatment.
Tombstone Retain non-content identifier, withdrawal basis and audit link where necessary to prevent re-ingest or republication.
Backups Daily incremental and weekly full backups to separate JOOUST-controlled on-premises storage.
Fixity Scheduled SHA-256 verification of canonical assets and release manifests; record exceptions and remediation.
Recovery Restore database, object store and ten representative assets within the 48-72 hour recovery objective.
11. Security, Privacy and Access-Control Implementation
 SEC-DM-01  Place identity profiles, consent evidence and precise geospatial data in protected 
schemas or enclaves.
 SEC-DM-02  Expose pseudonymous Agent identifiers to research workflows.
 SEC-DM-03  Apply row/object authorization to records, assets, transcripts, derivatives and exports.
 SEC-DM-04  Log authentication, views, downloads, changes, exports, publication and administrative 
overrides.
 SEC-DM-05  Encrypt on-premises volumes at rest and use TLS for all application and service traffic.
